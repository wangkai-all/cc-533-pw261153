# 后厨秤离线称重单 · 归单与回执演示

后厨秤离线时按**本机序号**暂存称重单，换班后时钟可能被校回去。本项目用虚构数据完整演示：
接收端先落原单、入库端按「设备身份 + 本机序号」归单、一张业务单据只占一个回执槽位，
以及断网跨班次后的重传对账。**仅使用 Node.js 内置模块，无第三方依赖。**

## 启动

```bash
node server.js          # 默认端口 3000
PORT=3111 node server.js # 端口取环境变量 PORT
```

服务只绑定 `127.0.0.1`。浏览器打开 `http://127.0.0.1:<PORT>`，依次点击：

1. **接收离线称重单** — 早班 3 张离线单上传，第 1 张回执丢包
2. **模拟掉线补交** — 跨班次 + 时钟回拨 + 换机重号 + 幂等补发 + 冲突/拒收异常
3. **查看称重回执** — 只读，列出全部回执槽位与状态

页面业务结果区带 `data-evidence-result` 属性，每次操作更新为机器可读证据串，
便于核对操作前后内容（例如 `netWeightTotal=46` → `97.1`、`pendingConfirmation=1` → `0`）。

## 测试

```bash
node --test
```

26 个用例覆盖正常流程与异常结果：幂等补发、回执丢包重投、时钟回拨跨班次、
换机重号、内容冲突、非法单据拒收、HTTP 顺序约束与错误码。

## 关键设计：两种确认方式怎么选

| 方案 | 问题 |
| --- | --- |
| 按已落库单据逐条确认（落库代理键） | 代理键是入库端内部生成的，上传方手里没有；重传时双方没有共同身份，回执丢了无法对账 |
| **按设备序号确认（本项目采用）** | 业务键 `deviceId#seq` 双方都持有，上传方可自行判重，回执按业务键对账；落库代理键仅作内部主键 |

**换机后重号怎么认**：业务键包含设备身份，`SCALE-A-01#1` 与 `SCALE-B-07#1` 是两张不同的单，
各占独立回执槽位。换机先做设备登记（`deviceHistory` 留痕），新设备从自己的 `seq=1` 起号也不会撞车。

**时钟回拨**：时间戳只用于展示，不参与唯一性与排序；序号单调递增，中班 `seq=4` 仍排在早班 `seq=3` 之后。

**补发只占一个位置**：接收端每次投递都落原单（`rawInbox` 留痕），入库端按业务键去重——
内容一致记 `duplicate`（不新增正式单、不新增回执），内容被篡改记 `conflict`（保留首单）。
回执槽位始终只有一个，丢包后重投的还是同一张回执（`deliveryAttempts` 累加，回执号不变）。

## 虚构场景的计算结果

| 指标 | 步骤①后 | 步骤②后 |
| --- | --- | --- |
| 入库正式单 | 3 | 5（新增中班 A#4、备用秤 B#1） |
| 净重总量 | 46.0 kg（早班） | 97.1 kg（早班 46.0 + 中班 51.1） |
| 待确认单据 | 1（R-0001 丢包） | 0（同槽回执重投成功） |
| 回执槽位 | 3 | 5（补发未产生新槽位） |
| 幂等补发 / 冲突 / 拒收 | 0 / 0 / 0 | 1 / 1 / 1 |
